# 기존 도구와의 차별점

과제 요구사항 중 "다른 도구와의 차별점" 항목이다.
비교 대상은 실무에서 C/C++ 에 흔히 쓰는 도구들이다.

## 1. 한 장 비교

| | Cppcheck / Flawfinder | Coverity / CodeQL | ChatGPT 에 코드 붙여넣기 | **ai-sast-userland** |
|---|---|---|---|---|
| 탐지 방식 | 패턴 매칭 | 컴파일 + 데이터플로 | LLM 단독 판단 | 규칙 매칭 → LLM 판정 → LLM 반박 |
| 빌드 필요 | 불필요 | **필요** | 불필요 | 불필요 |
| 대용량 저장소 | 가능 | 가능 | **불가능** (컨텍스트 초과) | 가능 (93.7% 사전 축소) |
| 오탐 억제 | 약함 | 강함 | **매우 약함** | 적대적 Verifier 로 분리 |
| 환각 위험 | 없음 | 없음 | **높음** | 라인 대조 + `needs_context` |
| 판단 근거 설명 | 규칙 ID만 | 경로 추적 | 자연어 (검증 불가) | 자연어 + 대조 가능한 라인 번호 |
| 커스텀 프레임워크 대응 | 규칙 추가 | 쿼리 작성 (난이도 높음) | 가능 | `SINK_RULES` 한 줄 추가 |
| 비용 | 무료 | 라이선스 고가 | 사실상 불가 | 배치당 약 3만 토큰 |

## 2. 핵심 차별점 3가지

### 2-1. "찾는 것"과 "판단하는 것"을 분리했다

Flawfinder 는 `strcpy` 를 **전부** 보고한다. `userland` 에는 22곳이 있는데,
대부분은 `sizeof` 로 경계가 잡혀 있어 안전하다. 그래서 실무자는
Flawfinder 결과를 안 읽는다.

반대로 LLM 에 코드를 그냥 던지면, 컨텍스트가 부족한 상태에서 판단을 강요당해
없는 취약점을 지어낸다.

이 도구는 **정규식이 찾고, LLM 이 판단한다.** 정규식은 428개 함수를
0원에 골라냈고, LLM 은 그중 판단이 필요한 것만 봤다.
`vc_cec_send_message` 의 `sprintf` 는 Flawfinder 라면 무조건 보고했을
코드지만, 이 도구는 `CEC_MAX_XMIT_LENGTH = 15` 상수를 추적해서 **안전하다고
증명하고 기각**했다.

### 2-2. LLM 이 LLM 을 반대신문한다

일반적인 "AI SAST" 는 LLM 한 번 호출하고 끝난다. 그 출력은 검증되지 않는다.

이 도구의 Verifier 는 **Analyst 의 주장을 반박하도록** 프롬프트가 설계돼 있다.

> *"You are rewarded for correctly rejecting false positives, not for agreeing."*

그리고 기계적 대조 규칙이 하나 걸려 있다 —
**Analyst 가 인용한 라인이 실제 코드와 다르면 환각으로 즉시 기각.**
이게 LLM 기반 도구의 최대 약점인 환각을 구조적으로 잡는다.

판정도 이분법이 아니라 3단(`confirmed`/`downgraded`/`rejected`)이다.
그래서 "지금은 안전하지만 여유가 0바이트"인 코드를 표현할 수 있다.
실제로 `io_net.c:134` 의 매직 넘버 `-4` 는 계산해보면 정확히 맞아떨어져
오버플로가 안 나지만, 포맷 문자열 정의가 바뀌면 검사가 조용히 깨진다.
Coverity 는 이걸 보고하지 않고, Flawfinder 는 그냥 `sprintf` 라고만 하며,
이 도구는 **"안전하지만 취약해지기 쉬움"으로 하향해서 남긴다.**

### 2-3. 릴리스 빌드의 실체를 본다

이 도구가 찾은 `vcilcs.c` 취약점 3건의 근본 원인은 이거다.

```c
vcos_assert(clen == sizeof(IL_PASS_BUFFER_EXECUTE_T) + exe->bufferLen);
memcpy(dest, buffer->buffer, exe->bufferLen);
```

`vcos_assert` 가 경계 검사처럼 보인다. 그런데
`interface/vcos/vcos_assert.h:239` 를 열어보면:

```c
#define vcos_assert(cond) (void)0
```

릴리스 빌드에서는 검사가 **사라진다**. 패턴 매칭 도구는 `vcos_assert` 라는
이름을 보고 "검증됨"으로 처리하거나 아예 모른다. LLM 은 매크로 정의를
추적해서 이걸 알아냈다 — Verifier 가 Context Broker 로
`vcos_assert` 심볼을 요청해서 실제 정의를 가져왔기 때문이다.

**"이름이 assert 니까 검사겠지"를 의심하는 것**, 이게 규칙 기반 도구가
못 하는 일이다.

## 3. 솔직한 열세

차별점만 쓰면 정직하지 않으니 밀리는 부분도 남긴다.

- **함수 간 데이터 흐름** — CodeQL 은 전역 호출 그래프로 taint 를 추적한다.
  이 도구는 함수 내부가 기본이고, 함수 밖은 Verifier 가 필요할 때
  일부만 조회한다. 여러 함수를 거치는 취약점은 놓칠 수 있다.
- **재현성** — 규칙 기반 도구는 같은 입력에 항상 같은 출력을 낸다.
  LLM 단계는 그렇지 않다. 그래서 디스크 캐시를 넣어 같은 코드에 대해서는
  결과가 고정되게 했지만, 근본 해결은 아니다.
- **컴파일 정보 부재** — 어떤 `#ifdef` 가 실제로 켜지는지 모른다.
  `vcos_assert` 건은 양쪽 정의를 다 확인해서 처리했지만, 일반적으로는
  빌드 설정을 모르는 게 약점이다.

그래서 이 도구의 현실적인 자리는 **Cppcheck 대체가 아니라
"1차 도구가 뱉은 노이즈를 사람 대신 읽어주는 2차 필터"** 다.
