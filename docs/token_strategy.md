# 토큰 절약 방안 — 설계와 도입 이유

## 실측 결과

`python3 run.py --repo ../userland-master --offline` 실행값이다.

| 배치 | 파일 통째로 넣을 때 | Sieve 통과 후 | 절감률 |
|---|---:|---:|---:|
| batch1 `host_applications` | 413,043 tok | 46,253 tok | **88.80%** |
| batch2 `containers` | 408,078 tok | 22,214 tok | **94.56%** |
| batch3 `interface` | 702,781 tok | 26,970 tok | **96.16%** |
| **합계** | **1,523,902 tok** | **95,437 tok** | **93.74%** |

Scout + Sieve 는 LLM 없이 **2.13초** 만에 277개 파일을 처리했다.

## 도입한 8가지 기법

### 1. 결정론적 사전 필터 (가장 큰 효과)
`sastagent/sieve.py`

싱크가 하나도 없는 함수는 **LLM 에 보내지 않는다**. 3,687개 함수 중
싱크가 걸린 건 428개(11.6%)뿐이다.

**도입 이유** — LLM 이 잘하는 건 "이 코드가 위험한가?"를 *판단*하는 것이지,
"`strcpy` 가 어디 있나?"를 *찾는* 게 아니다. 찾는 일은 정규식이 0원에 한다.
비싼 자원을 비싼 자원만 할 수 있는 일에 쓰는 것이 원칙이다.

### 2. 함수 단위 슬라이싱
`sastagent/slicer.py`

파일이 아니라 함수를 보낸다. `vcilcs.c` 는 3,000줄이 넘지만
`ilcs_receive_buffer` 하나만 보내면 90줄이다.

**도입 이유** — C 취약점의 대부분은 한 함수 안에서 판정 가능하다.
파일 전체를 보내는 건 40배의 비용을 내고 40배의 노이즈를 사는 것이다.

### 3. 긴 함수 축약 (shrink)
`slicer.shrink()`

160줄이 넘는 함수는 싱크 라인 기준 위아래 25줄 + 시그니처 8줄만 남기고
나머지는 `/* ... N lines omitted ... */` 로 접는다.

**도입 이유** — `parse_cmdline` 같은 함수는 400줄짜리 거대한 switch 문인데,
문제가 되는 case 는 두세 개뿐이다. 생략 구간을 **명시적으로 표시**하는 게
중요하다. 안 그러면 LLM 이 "이 함수엔 경계 검사가 없다"고 잘못 단정한다.

### 4. 정규화 해시 중복 제거
`sieve.normalize()` + `fingerprint()`

주석과 공백을 제거한 뒤 SHA-1 을 뜬다. 같은 코드가 여러 파일에 복제돼 있으면
**한 번만 분석하고 나머지는 결과를 재사용**한다. batch1 에서 4건이 접혔다.

**도입 이유** — 임베디드 코드베이스는 복붙이 많다. `userland` 도
`models.c` 가 두 곳에 존재한다. 같은 걸 두 번 분석할 이유가 없다.

> 다만 이 기법에는 한계가 있다. `models.c` 두 판본은 주변 코드가 미세하게
> 달라 해시가 갈렸고, 결과적으로 둘 다 분석됐다. **오히려 다행이었다** —
> 두 파일은 각각 패치가 필요한 '분기된 복제본'이기 때문이다.
> (리포트 B1-05 참고)

### 5. 2단계 모델 라우팅
`config.MODEL_CHEAP` / `MODEL_STRONG`

- **Analyst = Haiku 4.5** — 후보 전량을 빠르고 싸게 1차 분류
- **Verifier = Sonnet 4.6** — `not_a_bug` 로 걸러지고 남은 고위험만 정밀 검증

**도입 이유** — 후보의 상당수는 "명백히 아님"이라 값싼 모델로 충분하다.
비싼 모델은 판단이 어려운 소수에만 쓴다. 실제 배치에서 Analyst 는
후보 40건 전부를, Verifier 는 그중 일부만 처리한다.

### 6. 프롬프트 캐싱
`llm.py` — system 블록에 `cache_control: ephemeral`

공통 규칙집(`system_rulebook.md`, 약 400토큰)은 모든 호출에 동일하게 들어간다.
이걸 캐시로 지정하면 두 번째 호출부터 입력 토큰이 캐시 읽기 요금으로 바뀐다.

**도입 이유** — 배치당 40회 호출이면 규칙집만 16,000토큰이 중복된다.
한 번만 내고 재사용하는 게 맞다.

### 7. 디스크 캐시
`llm.py` — `(모델 + system + user)` 해시를 파일명으로 저장

같은 코드를 다시 스캔하면 API 를 안 탄다. CI 에서 반복 실행할 때
바뀐 파일만 실제 비용이 든다.

**도입 이유** — SAST 는 커밋마다 도는 도구다. 전체 재분석은 낭비다.

### 8. 출력 토큰 상한 + JSON 강제
`config.TOKEN_BUDGET` — Analyst 700 / Verifier 900

프롬프트에 *"Return ONE JSON object. No markdown, no prose."* 를 못 박고
`max_tokens` 로 물리적 상한을 건다.

**도입 이유** — 출력 토큰이 입력보다 비싸다. 모델이 친절하게 설명을 늘어놓으면
비용이 두 배가 되는데, 그 설명은 어차피 리포트에서 안 쓴다.
게다가 JSON 강제는 파싱 안정성도 같이 얻는다.

### 9. (보너스) Reporter 에게 소스를 안 준다
`agents.build_reporter_prompt()`

Reporter 는 구조화된 findings JSON 만 받는다. 원본 코드는 안 본다.

**도입 이유** — 보고서를 쓰는 데 소스가 필요 없다. 필요한 정보는 이미
Analyst/Verifier 가 추출했다. 여기에 소스를 다시 넣으면 배치당 수만 토큰이
그냥 사라진다. 덤으로, Reporter 가 소스를 보고 **새로운 취약점을 지어내는
것도 구조적으로 막힌다.**

## 절약과 정확도의 트레이드오프

| 기법 | 놓칠 수 있는 것 | 완화책 |
|---|---|---|
| 싱크 기반 필터 | 커스텀 래퍼 함수를 통한 취약점 | 규칙집에 사내 래퍼 추가 가능 (`SINK_RULES`) |
| 함수 단위 슬라이싱 | 함수 간 데이터 흐름 취약점 | Context Broker 로 호출자 on-demand 조회 |
| shrink | 생략 구간의 경계 검사 | 생략을 명시 표기 → LLM 이 `needs_context` 선언 |
| 해시 dedup | 미세하게 다른 복제본 | 정규화 강도를 낮춰 의도적으로 보수적 |

이 도구는 **완전성(completeness)보다 정밀도(precision)** 를 택했다.
오탐 100건은 아무도 안 읽지만, 확정 8건은 오늘 고칠 수 있기 때문이다.
